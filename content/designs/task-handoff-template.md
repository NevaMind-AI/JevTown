# 编剧任务交付模板

状态：交付格式提案。用自然语言写清玩法与文案，不要求编剧编写运行 JSON。

组织方式参考[剧本时间线](https://afterglow.xnnehang.top/story/timeline)：阶段有前后条件，独立调查、对白分支与可选操作另列。完整示例见
[S01 消磁门牌](s01-door-tag.md)。

## 1. 任务卡

| 字段           | 编剧填写                                               |
| -------------- | ------------------------------------------------------ |
| 任务编号／名称 | 稳定编号，以及玩家看到的名称                           |
| 交付状态       | 提案／待审台词／可制作；哪些设定尚待确认               |
| 所属内容包     | 本任务所属世界，是否依赖其他任务                       |
| 任务起因       | 玩家为什么遇到这件事，开场可以知道什么                 |
| 激活条件       | 一个可观察事件或明确条件；多个入口写清“任一”还是“全部” |
| 时间／地点     | 事件时机优先；只有确实需要作息或期限才写钟点           |
| 完成目标       | 玩家最终成功做了什么；不能只写“理解”“感动”             |
| 完成结果       | 确认的信息、物品去向、关系／后续变化；没有奖励就写无   |

## 2. 人物与物件

| 人物 | 场景／日常状态       | 已知事实             | 本任务中会做什么       | 不知道／不应提前说的内容 |
| ---- | -------------------- | -------------------- | ---------------------- | ------------------------ |
| 名称 | 地点、工作或休息状态 | 其亲历或有来源的信息 | 提示、作证、接收物品等 | 信息边界                 |

| 物件 | 初始位置／持有人 | 可做的操作               | 操作后去向／变化         | 素材状态             |
| ---- | ---------------- | ------------------------ | ------------------------ | -------------------- |
| 名称 | 地点及归属       | 查看、阅读、拿取、交付等 | 明确是否消失、转移或保留 | 已有／可复用／待制作 |

## 3. 阶段总表

| 阶段           | 背景概要         | 场景／NPC／目标      | 触发条件 | 玩家行为／对白概要   | 完成条件             | 效果／下一阶段           |
| -------------- | ---------------- | -------------------- | -------- | -------------------- | -------------------- | ------------------------ |
| 阶段编号及名称 | 只写此时可知的事 | 实际出现的人物、物件 | 何时开放 | 做什么、得到什么信息 | 哪个成功结果推进任务 | 事实、物品和目标如何改变 |

总表用于快速审阅，具体文案和操作以对应阶段卡为准。表格行的先后不自动表示前置；并行节点明确写“顺序不限”。

## 4. 阶段卡（每阶段复制一份）

### 阶段编号 · 名称

- **时间／场景：**
- **NPC／物件及状态：**
- **触发条件：**
- **玩家可见背景：**可直接放入任务面板的完整短段落，回顾起因和必要经过，不只写一句孤立的当前状态。
- **当前目标：**可直接显示的行动提示。

| 对白／操作编号 | 出现条件                   | 说话者／展示正文         | 玩家选项             | 成功效果                             |
| -------------- | -------------------------- | ------------------------ | -------------------- | ------------------------------------ |
| 稳定编号       | 具体条件，无则写“阶段开放” | 直接可用的台词或物件描写 | 按钮／选择的准确文字 | 每个选项分别写；离开或返回通常无效果 |

- **完成条件：**实际成功的动作或全部／任一材料条件；打开话题不等于确认，承诺交付不等于实物转移。
- **完成后：**下一目标、得到或失去的物品、保留的信息。
- **离开／拒绝／重复：**是否能回来、材料是否保留、是否重复发放。

阶段含独立节点时，每个节点都填写条件、台词、确认动作和结果；汇合处写明需要“全部”还是“任一”。提前取得的信息要明确是保留认可，还是必须再次实际操作。

## 5. 完成总结与分支

**完成背景：**玩家实际经历的起因、经过和结局；没有发生的可选事件不写成已完成。

**完成说明：**物件去向与后续提示。无额外奖励时明确写无。

| 情况                       | 玩家看到什么       | 保留什么／是否推进           |
| -------------------------- | ------------------ | ---------------------------- |
| 提前取得线索               | 对应的已知文案     | 是否认可，不要求工程自行猜测 |
| 取消、暂时离开、人物不在场 | 回来方式或缺项提示 | 已有进度和物件位置           |
| 重复确认或完成后再访问     | 简短回顾           | 不重复发放或完成             |

## 6. 工程转化备注（由工程补充）

编剧负责上面的事实、文案与操作后果。工程在这里登记：

- 场景、NPC、物件对应的现有 ID，以及待增加的实体。
- 哪些动作由现有能力承接，哪些能力尚缺；不得把提案字段当作已支持语法。
- 前置条件与完成条件分别映射到什么状态／成功事件。
- 已取得材料如何保存和认可，物件转移如何与任务结果保持一致。
- 暂未落实的内容及最小验收例，不把未实现行为标成可玩。

阅读顺序为“任务卡 → 总表 → 阶段卡”；工程不应为了转化再猜 NPC 说什么、玩家确认哪个选项、何时发物品或何时算完成。
