# Story 编写能力表 · MVP

主线仅保留 NPC 的 movement、dialogue、shop、schedule 能力；Story 持有对白、变量、任务、物品、线索与时钟。餐饮、演出、教学及其条件、事实和命令已移至
`experiment/tavern-agentic`，主线加载器拒绝这些配置。当前内容入口见[房间内容包](../public/content/remaining-time/README.md)。

归属：story authoring Skill，负责
`story.json`。本表的事实订阅、计数、条件和效果均用于 story，不是 scene 字段。引擎产生事实，story 声明如何消费；scene 编写参考
[Scene 能力表](SCENE_CAPABILITIES.md)。

只列当前实现能力，不把设计参考中的能力当作已支持功能。

**使用前必读：**
[内容合同](README.md)、本表、[实际样例](story.json)。实现依据：`prototype/content.ts`（加载校验）、`prototype/taskFacts.ts`（事实统计）、`prototype/world.ts`（执行）。当前 scene/story 均接受
`schema_version: "1.0"`；`content_version` 标识内容修订。本表随实现更新。

## 1. 内容归属

| 内容                               | 文件位置                       | 编写方式                                                      |
| ---------------------------------- | ------------------------------ | ------------------------------------------------------------- |
| 场景、实体 ID、anchors、门的目的地 | 读取 `scenes/*.json`           | 只读引用；变更需求交给 scene authoring                        |
| 初始场景与 anchor                  | `story.start`                  | `{ "scene": "room", "anchor": "start" }`                      |
| 剧情变量                           | `story.vars`                   | 声明布尔初值，例如 `has_pass: false`                          |
| 实体交互                           | `story.interactions[entityId]` | 台词、选项、条件和效果集中定义                                |
| 商品目录                           | `story.items[]`                | 商品 ID、名称、图片、品类、品质与描述；内容包内合并后 ID 唯一 |
| 商店定义                           | `story.shops[entityId]`        | 商店名与 offers；引用场景中已有、可交谈的非 portal 实体       |
| 任务                               | `story.tasks[]`                | 标题、说明、有序步骤与事实条件                                |

实体 ID 在内容包内唯一。story 直接引用它；没有交互条目的实体不能发起对话。portal 通过碰撞触发其唯一的 travel 选项，普通实体通过交互选择选项。默认须四向相邻；scene 可用
`interactionOffsets`
声明隔柜台等额外交互站位，台词与效果仍由 story 持有。E、点击人物与交互按钮共用运行时距离判定，成功交谈时双方自动转向。柜台占地、额外交互站位的完整配置与验收见
[Scene 能力表的“柜台、服务窗口”章节](SCENE_CAPABILITIES.md)；编排步骤见
[Story authoring Skill](../.agents/skills/story-authoring/SKILL.md)。这些空间字段归 scene／美术配方，不属于 story.interactions。

物件也通过 `interactions[entityId]` 编排：例如 `room.book` 在 scene 中使用
`character: "book"`，story 提供阅读 text 与 `effects: []`
的“合上”选项即可，不必声明任务。可重复阅读；一次性结果需要显式变量／条件。move_entity 要求目标实体在 scene 中声明
`movable: true`，与外观无关；省略 movable 等同 false。

固定座椅是场景内置交互：scene 的 seat 提供姿态与占用规则，不在同一椅子上配置 story.interactions 或 shops。坐下发出 interaction.started，可以按椅子 ID 编写交互任务；stand 是运行命令，不是 story
effect。固定坐客可通过 scene.seatedOn 绑定座椅并拥有自己的 story.interactions；台词不写到椅子上，也不改变其桌子占用。当前支持起始固定坐姿，不能编造 NPC 坐下／离席效果。完整合同见
[Scene 能力表“可坐座椅”](SCENE_CAPABILITIES.md)。

## 2. 商品、商店与背包

这是通用 JSON 能力，不需要为每种商品或商人增加源码。主线房间包暂无商店配置；交易回归使用
`tests/engine/shop.testHelpers.ts` 的独立小型商店，不加载酒馆。

以下拆分 story 示例给场景中已有的商人配置一种商品；商人本身及交互站位在 scene，欢迎语可以放在另一个 story 文件的 interactions 中：

```json
{
  "schema_version": "1.0",
  "content_version": "shop-example-1",
  "id": "shop-example",
  "vars": {},
  "interactions": {},
  "items": [
    {
      "id": "spring-water",
      "name": "雾岭山泉",
      "image": "assets/shop/spring-water.png",
      "category": "饮料",
      "quality": "日常",
      "description": "透明瓶身装着澄澈的山泉，蓝白纸标画着远山。"
    }
  ],
  "shops": {
    "merchant": {
      "name": "商店",
      "restock": { "intervalSeconds": 86400 },
      "offers": [{ "item": "spring-water", "buySeconds": 120, "sellSeconds": 60, "stock": 30 }]
    }
  }
}
```

| 字段                               | 规则                                                                                                                                                                                                                              |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `items`                            | 可选，最多100件；每件的 id/name/image/category/quality/description 都必需，未知字段拒绝。ID 内容包内唯一，文本遵守现有4000字符上限与保留字校验                                                                                    |
| `items[].initiallyOwned`           | 遗物可选布尔值；true 在新游戏时预置1件，供初始收藏或调试展示。默认不持有，不影响已有存档，不生成获得事件；实际效果仍需单独实现                                                                                                    |
| `items[].slot`                     | 遗物可指定1–31的固定格位；同一内容包内不得重复，普通物品不能声明。省略时按遗物在目录中的顺序编号；显式格位与默认编号冲突时拒绝加载。未持有仍显示固定问号格，线索不会揭示名称、图标或特殊效果                                      |
| `items[].kind / effectDescription` | 可选 `kind:"relic"` 将物品归入遗物收藏，并从普通背包中排除。`effectDescription` 仅允许遗物声明，用于展示特殊效果说明，不自动执行效果。持有数量沿用现有库存及存档机制，买入或 give_item 均可获得；省略 kind 的旧物品仍属于普通背包 |
| `items[].image`                    | public 下的 `assets/<目录>/<文件>.png`，沿用通用图片路径校验。品类、品质、描述只负责展示，不产生属性或食用效果                                                                                                                    |
| `shops`                            | 可选，最多100个，以实体 ID 为 key；实体必须存在、不是 portal 或 seat，并有 interactions 条目。一个实体只能合并一份商店定义                                                                                                        |
| `shops[id].name / offers`          | 名称必需，offers 为1–100项；一店同一商品只能出现一次，item 必须在 items 中定义                                                                                                                                                    |
| `buySeconds`                       | 买入一件支付的生命秒数，整数1–604800                                                                                                                                                                                              |
| `sellSeconds`                      | 卖出一件获得的生命秒数，整数0–buySeconds；每件可以单独定价，并非引擎固定打五折                                                                                                                                                    |
| `stock`                            | 新运行的初始库存，也是定期补货的目标数量，整数0–9999；不是无限库存标记                                                                                                                                                            |
| `shops[id].restock`                | 可选 `{ "intervalSeconds":86400 }`；存在即启用，省略即关闭。周期为整数1–604800秒，单位是游戏剧情时间；例如每24小时                                                                                                                |

### 定期补货与游戏时间推进

补货依据已结算的State.storyTime。分段时钟配置示例：

```json
"clock": {
  "realSecondsPerTick": 30,
  "gameSecondsPerTick": 600,
  "idlePauseSeconds": 60,
  "initialBalanceSeconds": 432000,
  "startTimeSeconds": 64800
}
```

realSecondsPerTick与idlePauseSeconds为1–3600整数，gameSecondsPerTick为1–86400整数；初始余额为非负安全整数，起始时刻为0–604800，省略初值仍为7小时和18:00。每累计30秒有效模拟时长，一次推进600剧情秒并扣除600生命秒。HUD只显示已结算的时刻与余额，交易及报酬即时结算。State.clock保存当前流速和未完成一段的elapsedMs，暂停、保存、读档与回放保留进度；不把移动再计一笔耗时。

后台及背包、任务、商品等弹窗暂停；普通对话期间周围人物和世界时钟继续运行，生命按段结算，玩家不能移动。超过idlePauseSeconds无键鼠操作时整局暂停并停止新增模拟记录，输入恢复且不补算离开时间。界面不再提供时间调速面板，反引号打开的开发控制台仅保留 help，tp 暂停开放，待 agentic 合入且 record 方案确定后再考虑扩展；为已有记录回放保留底层调速命令
`{"requestId":"clock-1","type":"setClockSpeed","seconds":60}`，seconds为1–3600，改变一段所需的运行秒数，保留进度比例并进入记录，游戏段长度不变。旧rate配置继续按原规则运行，与分段字段互斥。

`R`打开等待窗口，`T`保留任务入口。等待界面用固定1–24小时、步长1小时的滑条选择，默认1小时；范围不随生命余额变化，余额不足只禁用确认。显示当前时刻、结束时刻、消耗及剩余余额，消耗包含本段已积累但尚未结算的时间。命令为
`{"requestId":"wait-1","type":"waitUntil","time":79200}`，time为绝对剧情秒，须晚于包含段进度的当前逻辑时刻，最多推进7天且余额足够；移动或交谈时不能等待。分段时钟下按当前流速换算需要推进的模拟时长，处理人物作息及补货，并结清段进度。一个等待只提交一个事件，失败回滚，重复请求不重复收费；途中任务触发保留。分段时钟单次等待最多处理200000个截止点，超限须缩短等待或加快流速。旧记录保留原等待语义。

以下显式运行命令仍可推进补货：

```json
{ "requestId": "wait-one-day-001", "type": "advanceStoryTime", "seconds": 86400 }
```

这是 `world.execute`
接受的**运行命令**，不是 story 的 effect，也不是计时器配置。seconds 为1–604800的整数，只能向前推进；同一 requestId 的相同命令只执行一次。调用方不要直接改写 storyTime，否则会绕过补货及日志。此命令不会推进移动模拟时间，也不会扣除生命余额；它可在交谈期间执行，当前界面没有新增等待／跳日按钮。既有 nextScene 的一小时推进也共用补货检查，其午夜终止限制保持不变。

- 新运行从18:00开始，则24小时补货的首次时刻是次日18:00；切场景、打开商店、买卖都不重置周期。
- `State.commerce.nextRestock[商人ID]`
  保存下一次补货的绝对游戏秒数。仅为启用补货的商店创建条目；所有商店都关闭时不增加该字段，保持旧记录形状。
- 时间推进到达或跨过截止点时，检查所有到期商店（不要求玩家在场）。每种店存更新为
  `max(当前数量, offers.stock)`，不动玩家物品；卖回形成的超额库存保留。
- 一次跳过多个周期只补到目标一次，不按错过的天数堆积商品；下一时刻保持原周期相位并推进到当前时间之后。
- 剧情时间、店存与下次补货时刻一起提交和记录，失败全部不变。当前正在交谈的商店到期时递增交互版本，防止旧页面提交过期交易。
- 回放使用记录中的advance与推进命令，不读取现实时间重新补货。检查点与续玩保留下次补货时刻；暂停期间不补货。

运行规则：

- 玩家初始背包为空。买入扣余时、减店存、加背包；卖出加余时、加店存、减背包。三者一次提交，失败全部不变；数量减到0时移除背包条目。
- 单笔数量1–99，每种物品的玩家数量和每店库存均不超过9999。买入不能透支；这与既有剧情 `pay_time`
  允许透支的规则分别处理。商人当前没有独立资金余额，回购只受持有数量、店存上限与玩家余额安全整数上限约束。
- 必须已与该商人交谈，并且仍处于允许的交互站位；玩家和商人不能正在移动／过门。界面显示“看看商品”，可切换买入、卖出和背包。数量使用1–99整数滑条，支持拖动、−/+微调和键盘方向键；上限固定99，超出库存／持有量或余额时禁用确认，不会擅自缩小滑条范围。卖出只列本店 offers 中玩家实际持有的物品。
- `1` 或右下角背包按钮查看普通物品；`2`
  打开独立遗物收藏，显示已获得遗物及效果说明。两个入口在空背包时也可用，H 隐藏快捷栏；回放中可只读查看。离开商人后没有买卖入口。面板暂停本地模拟并隔离移动／E／R／T 热键；Esc 或 × 关闭商品面板，原交谈保留，任务面板的 Esc 规则不变。
- 命令为 buy/sell，携带 target、item、quantity、当前 interactionRevision 和 requestId。价格由运行时查配置，客户端不能传价格。成功交易递增交互版本，旧版本拒绝；相同 requestId 与相同命令只执行一次。
- 定义留在不可变 story；实际数量存于 `State.commerce.inventory` 和
  `State.commerce.stock`。记录、检查点、回放及续玩包含这些状态与请求去重缓存。未声明商品的旧内容不增加 commerce 字段，保留原记录形状。
- 当前支持剧情 `give_item`
  赠送，见效果合同；食用、装备、丢弃、商品条件解锁及购买任务事实尚未实现。刷新仍是新运行；延续背包应导入运行记录并从指定位置继续。

编写后同时检查：商品图存在；scene 站位可达；买一件的扣时与数量一致；卖一件的回收值与库存一致；无余额／无库存／无物品时失败；同一请求重复不会重复结算；回放后继续交易一致。实际配置当前使用六件商品、有限库存，卖价为各买价的一半。

## 3. 任务可用事实

| `event`               | 字段                   | 含义与产生时机                            | 示例用途                       |
| --------------------- | ---------------------- | ----------------------------------------- | ------------------------------ |
| `movement.completed`  | `direction`            | 成功抵达相邻格；值为 `up/down/left/right` | 四向练习、向某方向走若干格     |
| `interaction.started` | `entityId`             | 成功开始与可交互实体交谈；不是对话结束    | 找 N-07 交谈、与不同居民打招呼 |
| `choice.confirmed`    | `entityId`, `choiceId` | 显式选择的效果成功执行后                  | 确认领取许可、选择某个回答     |
| `scene.entered`       | `sceneId`              | travel 成功进入场景                       | 到达走廊、访问不同场景         |

- 初始加载不产生 `scene.entered`。
- portal 碰撞会执行效果并产生 `scene.entered`，但当前不产生 `interaction.started` 或
  `choice.confirmed`；门任务使用场景到达事实。
- 失败、取消及去重后的重复请求不增加进度。
- 显式选项包含 travel 时，当前先处理 `scene.entered`，随后处理 `choice.confirmed`；两者是独立事实。

## 4. 通用统计与筛选

| 字段      | 必需 | 当前规则                                                           |
| --------- | ---- | ------------------------------------------------------------------ |
| `event`   | 是   | 上表中的一个事实名称                                               |
| `count`   | 是   | 1–1000 的整数，达到即完成                                          |
| `where`   | 否   | 字段与字符串值的等值筛选；多个字段全部满足                         |
| `collect` | 否   | 收集该事实字段的不同值，去重后计数                                 |
| `items`   | 否   | 仅可搭配 collect；`[{value,label}]` 同时限定可收集值和提供清单标签 |

没有 collect 时，每条匹配事实计一次。有 collect 时，重复值不重复计数。items 的 value 必须唯一，数量至少等于 count；因此它不只是 UI 文案。若只想累计次数，不要配置 items。

### 组合示例

| 目标                     | condition                                                                               |
| ------------------------ | --------------------------------------------------------------------------------------- |
| 四个方向各走过一次       | `{"event":"movement.completed","collect":"direction","count":4}`                        |
| 向右成功走三格           | `{"event":"movement.completed","where":{"direction":"right"},"count":3}`                |
| 与 N-07 交谈两次         | `{"event":"interaction.started","where":{"entityId":"n07"},"count":2}`                  |
| 与三个不同实体交谈       | `{"event":"interaction.started","collect":"entityId","count":3}`                        |
| 确认 N-07 的 permit 选项 | `{"event":"choice.confirmed","where":{"entityId":"n07","choiceId":"permit"},"count":1}` |
| 进入走廊                 | `{"event":"scene.entered","where":{"sceneId":"corridor"},"count":1}`                    |
| 访问两个不同场景         | `{"event":"scene.entered","collect":"sceneId","count":2}`                               |

不同实体/场景数量必须在内容中实际可达。加载器检查 entityId/sceneId 引用及方向枚举；目前不验证 choiceId 是否存在，也不证明任务一定可完成，作者需核对并试玩。

## 5. 任务执行规则

| 项目     | 规则                                                                                                                                                                      |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 任务声明 | `id/title/description/steps`，可选 `trigger/background/completion`；任务 ID 唯一，步骤 ID 在任务内唯一。步骤可选 `background/description`，文本沿用非空、最多4000字符校验 |
| 顺序     | 每个任务仅当前未完成步骤接收事实，一条事实最多推进该任务一个步骤                                                                                                          |
| 多任务   | 同时运行，同一事实可以推动多个任务                                                                                                                                        |
| 历史行为 | 当前步骤激活前的行为不追溯补算                                                                                                                                            |
| 记录     | 每步保留 count 和收集到的 values；任务保留完成步骤 ID                                                                                                                     |
| 生命周期 | 切图保留；自动存档、回放与续玩保留进度；新时间线重新开始                                                                                                                  |
| 展示     | TaskBoard 只读取已完成步骤和当前步骤，未来步骤不出现在清单或总进度中；T 打开当前背景、完整描述、已知步骤、计数与 items 标签                                               |

编排约定：有前置关系的阶段放在同一 task 的 steps 中；互不依赖的目标拆成多个 task。例如移动练习与 E 交谈分别成任务，可任意顺序完成；“领证 → 隔壁重逢”保留为同一任务的顺序步骤。多个收集目标若互不依赖，也分别声明任务，无需新增并行语法。步骤顺序控制进度统计，不自动禁止玩家提前操作；需要限制操作时，另用选项条件或引擎规则。

### 分阶段任务叙述与提示

任务顶层的 `background`（可选）和 `description`
是初始叙述。每个阶段的 background 应是一份从任务起因到当前的完整回顾，包含此前已经获知的关键信息；description 说明当前要做什么。当前步骤可以分别覆盖这两个字段；省略的字段回退到任务顶层，不继承前一步的覆盖文案。例如：

```json
{
  "id": "visit",
  "text": "进入走廊",
  "background": "你已经取得通行许可，可以离开房间。",
  "description": "走到房门进入走廊。",
  "condition": { "event": "scene.entered", "where": { "sceneId": "corridor" }, "count": 1 }
}
```

编写时只叙述该阶段已经得知的事情，不在初始背景、描述、标题或当前目标中提前透露后续奖励、人物关系与任务安排。已完成步骤保留勾选，当前步骤及其 items 清单视为已知，后续步骤在前一步完成后才出现。背景与描述随当前步骤切换，支持换行；标题保持任务身份。

前端按成功记录前后的任务状态生成左侧提示：激活时“新任务”，计数增加或阶段切换时“任务更新”，最后一步完成时“任务完成”。更新提示显示任务标题及当前已知目标；多次计数目标附带当前计数，不展示未来步骤总数。同一记录内每个任务最多一条提示，完成优先；复用获得提示的动画与声音。失败、重复请求、不增加计数的行为不提示；读档与回放定位只恢复进度，正常回放经过进度事件时照常提示。

阶段文案保存在固定内容中，仍由既有 tasks 状态确定当前阶段，不新增任务记录字段。旧内容没有覆盖文案时使用原 description；新文案需要新开时间线加载。任务可配置
`completion:{background:"完整经过与结果",description:"完成后的状态与可做事项"}`，两个字段均为非空正文。完成后改用这份总结，保留在任务面板中并标记已完成，不占用当前目标栏，也不会重新激活。总结要覆盖任务起因、关键行动和最终结果，使玩家跳过中途对白后仍能回顾全貌；不把未实际执行的可选行为写成已发生。未配置 completion 的旧触发型任务仍沿用完成后隐藏的行为。

### JSON条件触发任务

任务可声明`"trigger":{"var":"room_available","equals":true}`，复用布尔条件：变量满足后激活，之前隐藏且不消费步骤事实；激活状态保留。任务激活后的步骤从后续事实开始统计，因此由领奖变量开启的安顿任务只需编排上楼、查看床。前端从记录中activated首次变为true的事件生成“新任务”浮动提示，复用获得提示音；读档与定位不重新通知已激活任务。

对白／选项可用
`"when":{"task":"help_lina","step":"accept"}`：只在任务已激活且当前步骤为accept时匹配。触发前、进入后续步骤或完成后均不匹配。task和step必须引用已定义任务／步骤；可用于普通对白、选项和已有通行条件入口。

## 6. 交互条件与效果

**选项条件与任务统计条件是两个不同位置的语法。** 选项／条件对白的 `when`
支持布尔变量等值或上述当前任务步骤条件：

```json
"when": { "var": "has_pass", "equals": true }
```

| effect        | 参数                                             | 行为                                                                                                                                                     |
| ------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `set`         | `var`, `value`                                   | 设置已声明布尔变量                                                                                                                                       |
| `pay_time`    | `seconds`                                        | 从唯一生命余额扣非负整数秒，允许透支，拒绝不安全整数结果                                                                                                 |
| `grant_clue`  | `clue`                                           | 获得 story.clues 中已定义的线索ID；同一条只记录一次。与其他效果原子提交，失败全部回滚                                                                    |
| `give_item`   | `item`, `quantity`                               | 赠送已定义商品1–99件，背包单种上限9999；不扣玩家余额或商店销售库存，溢出则整个选项回滚                                                                   |
| `sleep`       | `selectHours:true`、`seconds`或`nextDayAt`三选一 | 自选1–24个整小时、固定睡眠1–86400游戏秒，或睡到次日指定时刻（0–86399秒）。必须单独作为选项的唯一效果；确认后复用等待结算，扣生命并推进世界，失败原子回滚 |
| `travel`      | 无                                               | 使用当前实体portal的场景和anchor；每选项最多一次                                                                                                         |
| `move_entity` | `entity`, `path`，可选 `via` / `arrival`         | 对话选项启动可移动实体的逐格路线，例如 `{"op":"move_entity","entity":"n07","path":[[5,6],[6,6],[6,5],[5,5]]}`                                            |

移动路线为 1–100 个场景内整数坐标，连续点必须四向相邻；执行时首点必须紧邻实体当前位置。目标必须是当前场景的非 portal 实体，已有路线时拒绝重复启动。效果提交代表路线已启动，不代表抵达；后续效果不会等待路线结束。每个模拟 tick 最多前进一步，受阻等待重试；地图边界、实体、玩家及其目标格、保留 anchors 不可占据。行进中的 NPC 暂不可交互。切图保留路线，重置清空；当前UI在控制锁定或弹窗期间暂停模拟，普通对话期间其他NPC路线继续运行。路线可带
`via`（同场景 portal 实体 ID）与
`arrival`（目标场景的 NPC 到达 anchor）；终点必须紧邻门。走完后重新检查门条件与目标占用，允许则过门，否则等待。NPC 到达点建议与玩家分开；此过程只检查通行条件，不执行门的其他效果。暂不支持自动寻路及抵达任务事实。

效果按列表顺序在草稿中执行，全部成功才提交。执行时重新检查条件与交互版本；普通选项执行后关闭交互。portal 需要恰好一个包含 travel 的选项，条件不满足时阻挡并显示交互 text。

### 客房与睡眠

普通物件交互可声明
`{"op":"sleep","selectHours":true}`，打开与等待共用的1–24小时滑条，默认8小时。确认时 `choose`
命令额外携带
`hours`（1–24整数）；引擎重新检查床边交互、选项条件、版本与余额，再从包含段内积累的当前逻辑时刻计算目标。只有该效果允许提交 hours，缺失或越界会拒绝，不允许客户端覆盖普通选择或固定睡眠的时长。

旧内容仍可声明 `{"op":"sleep","seconds":28800}` 或
`{"op":"sleep","nextDayAt":57600}`，保持固定时刻确认。固定时长从包含段内积累的逻辑时刻起算，向上取整到秒；nextDayAt总是当前逻辑日期的次日，不是最近一次该时刻。三种形式都必须是选项的唯一效果。

执行须仍在物件旁交谈，不能坐着或移动；引擎在草稿中结束交谈后复用waitUntil，处理期间人物作息、补货与任务，最后提交choice.confirmed。余额不足、等待预算超限或其他失败全部回滚，取消预览不执行选择。费用含本段未结算的时间，当前客房免房费；不附加恢复效果。

当前睡眠配置见 `public/content/remaining-time/stories/unit-404.json`。

### 首次招呼与随机对白

交互可声明
`firstText`：首次成功交谈时前置这段介绍，再显示当前环境对白；后续见面与返回主话题只显示环境对白。`State.greetedEntities`
按实体记录已经介绍过的对象，取消交谈也不重复介绍，读档保留。

交互、topic 及条件 reply 可声明非空
`variants:["短句一","短句二"]`（最多100句，每句沿用正文长度限制）。先选第一条匹配 reply，再从该条的 variants 中抽一句；没有 variants 时使用 text，不继承其他条目的随机池。随机数使用独立的
`State.dialogueSeed`，初次以当前模拟时间与剧情时间初始化，使用32位LCG计算，后续状态随记录保存。对白只在交谈或切换话题时选择，界面刷新不重新抽取。

### 对话话题

交互可声明
`topics:{help:{text:"……",replies:[{when:条件,text:"……"}]}}`，正文与条件对白规则同交互开场。选项可声明
`opens:"help"` 切入话题，`topic:"help"` 限定只在该话题显示，`opens:"root"`
返回日常开场；root 为保留名称。省略 topic 的选项仅在主话题显示。例：

```json
{
  "id": "open_help",
  "text": "听说老板你找我，有什么事嘛？",
  "when": { "task": "help_lina", "step": "accept" },
  "opens": "help",
  "effects": []
}
```

话题导航的 effects 必须为空，切换保留交谈、更新正文与交互版本，不产生 choice.confirmed；任务由话题内的实际确认选项推进。返回主话题或重新交谈时恢复日常开场。State.dialogueTopic 可选记录当前话题，结束交谈时移除，存档与回放保留。话题选项仍独立检查 when，话题名必须引用同一交互中已声明的 topic。商品入口只在主话题显示。旧内容不声明 topics 时保持原行为。

### 分阶段对白与一次性谢礼

交互可选
`replies: [{when,text}]`，使用与选项相同的布尔或任务步骤条件。开始交谈时按数组顺序取第一条匹配对白，全部不匹配则使用原
`text`。省略 replies 的旧内容行为不变。

`give_item`
示例：`{"op":"give_item","item":"citrus-soda","quantity":1}`。它与同选项的变量写入原子提交；一次性赠送需由
`when`
控制，并在成功后关闭领取变量。背包满、版本过期、重复领取不会消耗领奖资格或再次发物品。礼品由剧情提供，不与有限销售库存绑定。

### 遗物线索与固定收藏

story（包括拆分文件）可声明
`clues: [{"id":"old-ghost-location","slot":1,"text":"赌坊的老鬼保管着一件遗物。","source":"绯月 · 酒馆柜台"}]`。线索 ID 在内容包内唯一；slot 为1–31，允许在该格遗物尚未编写时先配置消息。每条必须有正文及来源，列表沿用100条上限。

NPC对话、物件阅读等选项可用 `{"op":"grant_clue","clue":"old-ghost-location"}`
授予线索。只有执行成功后才计入
`State.clues`，运行状态仅存去重后的ID，正文与来源留在固定版本内容里。不同来源使用不同ID，即使属于同一格也分别累积；重复授予同一ID不增加数量。任务仍可用 choice.confirmed 追踪具体询问选项。

收藏按31个固定格位展示，未知格也能选择、查看已获线索及来源。持有遗物后揭示图标、名称、故事与效果说明，获得顺序不改变位置。线索和物品持有独立，线索不会自动赠送遗物。自动存档、快照、回放和续玩保留线索；定位只恢复对应位置的线索状态。

当前样例见
`public/content/remaining-time/stories/s01-door-tag.json`。新增剧情须开启新时间线，旧房间存档继续使用嵌入内容。

## 8. NPC 每日作息

`story.schedules` 按 NPC
ID 配置每天的离场、返回时间；可拆到单独 story 文件，同一 NPC 不允许重复定义。主线不包含随机食客或营业系统。

```json
"schedules": {
  "worker": {"scene":"room","sleepAt":82800,"wakeAt":46800,"entrance":[25,18],"home":[22,8]}
}
```

- `sleepAt`、`wakeAt`
  是一天内的游戏秒数（0–86399），不能相同，支持跨午夜；上述示例为23:00离场、次日13:00返回。按包含段内进度的游戏时间判断，每日循环。
- `scene`、`entrance`、`home` 定义场景、出入口与返回位置，须可通行且有路线；NPC 必须声明
  `movable:true`。只支持同场景往返，不支持跨场景作息路线。
- 休息时结束该 NPC 的交谈，沿可达路线离场；离场期间不显示、不碰撞、不可交易。返回时检查入口、路线和动态占位，受阻则等待；不重置任务或相识状态。
- `State.schedules`
  保存 active/leaving/away/returning；普通推进、主动等待、睡眠共用作息规则，快照与回放保留阶段和路线。未配置 schedules 的旧内容保留原行为；编辑配置后需开启新时间线。

## 9. 编写边界与扩展流程

当前没有数值求和、任意时间窗口、任意表达式、任务 OR 分支、通用 all/any 条件树、自动奖励配置或任意自定义事件。不要把 v2 中的同名概念直接套入当前内容。

1. 先尝试用本表的事实、筛选、计数和集合组合目标。
2. 缺少真正的游戏事实或统计方式时，提出能力需求与最小样例，由引擎开发扩展；编剧不直接修改后端。
3. 同步更新运行时、加载器、测试、本表及版本支持说明。新增事件/字段也属于协议扩展，旧引擎不一定支持。
4. 新增可选能力须保持旧内容行为；改变现有字段含义、单位或执行顺序属于破坏性变更，应升级主版本并明确迁移路径。
5. 发布前核对引用、步骤顺序、实际可达数量、重复触发及取消路径，并执行 `npm run test:prototype`
   和样例试玩。
