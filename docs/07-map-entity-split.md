# The Map / Entity Split

`applies to: 04 (2.0) and 05 (a1.0)`

**This is substrate, not a branch.** `06` §3 lists "map interface: named anchors, never raw
coordinates" as shared by both branches. This document specifies that interface, and in
doing so reverses one decision each branch made independently: `04` §6.4's merge of map
decoration into `entities`, and `05` §3's tier (d).

It amends, and takes precedence over, `04` §6.4 and §12 rule 7–8, and `05` §3 (tier d),
§4.2 (`origin`), and §12 rules 3–4, 8 and 10.

---

## 1. The claim

The world file should describe **story**. The map file should describe **terrain**. An
entity earns a place in the world file by being something a model can read, write, or reason
about; everything else is tiles.

Both branches drifted away from this for the same reason — merging decoration into
`entities` makes the format *complete*, and completeness is aesthetically attractive — and
both then had to defend against the consequences rather than remove them. `04` §6.4 defends
with pipeline discipline and prompt filtering. `05` §3 defends by giving decoration a tier
with every field stripped out. Neither defence addresses what the merge actually costs,
which is §2.

---

## 2. What the merge costs

### 2.1 A decoration entity is a re-encoding of a tile

`05` tier (d), stated in full (`05` §4.1):

```json
{ "id": "oak_04", "kind": "prop", "anchor": "square_ne", "sprite": "oak",
  "physics": { "blocks_movement": true } }
```

No `state`, no `persona`, no memory, no name, no inference. It carries a sprite and a
collision bit. The tile layers already carry both, at roughly a tenth the bytes, and they
carry them in a form the renderer and the pathfinder already consume
(`src/components/PixiStaticMap.tsx:47`, `convex/aiTown/movement.ts:178`).

The objection is not that a world with three hundred oaks is tedious to author. It is that
each oak is stored **twice** — once in `objmap`, once in `entities` — and the second copy is
the expensive one:

- Entity `physics` is read by the tick loop, so it lives in the world document (`05` §8),
  which is `ctx.db.replace()`d in full every step (`convex/aiTown/game.ts:300`). Decoration
  turns a 1 Hz full-document rewrite into a function of map size rather than cast size.
- The world document caps at 1 MB (`05` §9.5). Tile layers live in the `maps` row, written
  once at init (`convex/init.ts:70-80`), and never enter that budget.
- Entity creation goes through the input log. Three hundred `createEntity` inputs at world
  init is three hundred rows through the OCC hotspot `06` §5.4 already flags.

**Under this split, entity count scales with the story, not with the map.** That is the
property worth protecting, and it is what makes the per-step rewrite affordable.

### 2.2 There is no collision layer — this is the real blocker

Collision today is derived from *visual non-emptiness*:

```ts
for (const layer of map.objectTiles) {
  if (layer[Math.floor(position.x)][Math.floor(position.y)] !== -1) {
    return 'world blocked';
  }
}
```
— `convex/aiTown/movement.ts:178-180`

Two consequences, one cosmetic and one fatal.

Cosmetic: a purely decorative object tile — a rug, a painted floor, a shadow — blocks
movement today, because the engine cannot tell "drawn above the ground" from "solid."

Fatal: **a story prop drawn into `objmap` can never open.** `mill_door` (`05` §4.1) sets
`physics.blocks_movement: false` when Alice forces it, and the pathfinder keeps refusing the
tile, because the static layer still has a door sprite on it. The `05` §6.2 example — "the
same call that decides Alice forces the door must also tell the pathfinder the door no
longer blocks" — does not work against the current collision rule.

The workaround is authoring discipline: never paint an object tile under a story prop. That
fails silently, in a file generated by a tool, reviewed by nobody, and the symptom is an
agent that mysteriously refuses to walk through an open door. §5 replaces it with structure.

### 2.3 Entities cannot span tiles

An `anchor` is a point. A portcullis three tiles wide, a bridge, a barricade, a table —
none of them are expressible, and the natural fix (an entity per tile, sharing an `id`
prefix) breaks the "one entity, one prose state" model that `05` §5 rests on: three door
entities have three states that can disagree.

Note the map layer already solved this. `animatedsprites` carries `w`/`h`, and the windmills
in `data/gentle.js` are 208×208 px — six and a half tiles square. Multi-tile is a thing the
tile layer is good at and the entity list is not.

### 2.4 Why `04` §6.4's defence does not cover this

`04` §6.4 gives two reasons the merge does not swamp the format:

> 1. The format has one array; the pipeline has two producers. […] The writer agent's prompt
>    is filtered to story entities plus a manifest of legal anchor ids and prop ids — it
>    never sees three hundred trees.
> 2. `origin` marks provenance so a regeneration pass can replace story entities without
>    clobbering map output.

Both are correct and both address the same problem: **the writer agent's context**. Neither
addresses storage, the per-step rewrite, the input log, collision, or multi-tile. The
argument establishes that the merge is survivable at prompt time; it does not establish that
it is worth doing.

And its own mechanism is the tell. If the pipeline has two producers, the prompt is filtered
to one of them, and `origin` exists to keep a regeneration pass from clobbering the other —
then the two producers are already writing two different things, and the single array is
holding them apart with a flag. Give them two files.

## 3. The split

| Layer | Owns | Authored by | Artifact | Written |
|---|---|---|---|---|
| **Map module** | terrain, decoration, static collision, ambient animation, **anchor table** | a person, in Tiled | generated `.js`, e.g. `data/gentle.js` | once, at world init |
| **World file** | every entity a model may read, write, or reason about | the writer agent | `world.json` (`2.0` or `a1.0`) | at init; mutated through inputs |

**The rule, stated once:** *an entity belongs in the world file if and only if some model
call could take it as input or produce it as output.* Anything with `state`, `persona`,
`description`, memory, or god reachability qualifies. Everything else is a tile.

Applied to `05` §3, tier (d) disappears — it is precisely the set of entities the rule
excludes, and `05` §3.2 already derives inertness from the absence of `state`. An entity
that is inert *and* invisible to every prompt has nothing left to be. The taxonomy becomes
three tiers, and each remaining tier is defined by what it costs in inference:

| Tier | `kind` | `mobile` | Cost |
|---|---|---|---|
| (a) mobile agent | `actor` | `true` | inference, its own turns |
| (b) fixed agent | `actor` | `false` | inference, its own turns |
| (c) passive prop | `prop` | — | inference, inside another agent's call |

`05` §3.1's third argument — "how many inference-bearing entities does this world contain
should be one field lookup" — becomes stronger: it is now `entities.length`.

`origin` (`04` §6.4, `05` §4.2) becomes vestigial. With one producer per file, provenance is
the filename. **Drop it from both branches.**

## 4. The anchor table

This is the interface, and it is the part worth getting right. It is not a lookup table
bolted onto the map export; it is the contract between a human authoring geometry and a
model authoring story, and it is the reason the split composes instead of producing two
layers that fight.

### 4.1 Shape

The map module gains one export:

```js
export const anchors = {
  mill_yard: {
    x: 12, y: 20, w: 6, h: 4,
    description: "The packed-dirt yard on the mill's south face, bounded by the river to the east.",
  },
  great_hall_hearth: {
    x: 31, y: 8, w: 2, h: 1,
    description: "A stone firepit set into the hall's north wall, always lit.",
  },
  mill_entrance: {
    x: 14, y: 19, w: 1, h: 1,
    description: "The mill's north doorway.",
  },
};
```

`x`/`y` are tile coordinates in the same orientation as the tile layers — `layer[x][y]`,
per `data/convertMap.js`'s transpose and `mapwidth = bgtiles[0].length`. `w`/`h` are in
tiles and default to 1.

### 4.2 Anchors are rects, and that is what solves §2.3

An entity bound to an anchor **occupies the whole rect**. A door is a 1×1 anchor; a
portcullis is 3×2. `blocks_movement: false` clears the rect; `true` sets it. One entity, one
prose state, one physics projection, any footprint.

The world file still contains no tile coordinates, so `04` §6.4 and `05` §4.2's promise —
"this format never contains raw tile coordinates" — holds exactly as written. It is now
load-bearing rather than aspirational, because the anchor is the only way to say where
something is.

For a mobile actor, `spawn: { "anchor": "mill_yard" }` means *a free tile inside that rect*.
This narrows `Player.join`'s current search, which samples uniformly over the entire map and
retries ten times (`convex/aiTown/player.ts:190-201`). It remains a PRNG draw and stays on
`05` §10's list of sources to seed.

### 4.3 `description` is the writer agent's prompt, not documentation

The prose on each anchor is what makes this an interface rather than a storage detail. The
writer agent's context becomes:

```
world_rules
+ the anchor manifest  (id + description, every anchor in the map)
+ the character/sprite manifest
```

and it authors entities that reference anchors by name. It never sees a tile, never sees
three hundred oaks, and cannot place anything anywhere the map did not sanction. `04` §6.4
achieved the same filtering with a projection over a merged array; here it falls out of the
file boundary, with no `origin` flag and no filtering step to get wrong.

This also gives the map author a real job in the story pipeline: naming and describing the
places that may carry story is an authoring decision, and it is the one place a person
constrains what the model can write.

### 4.4 Authoring flow

Tiled object layers are named rectangles. That is already the anchor table.

```
Tiled .json  ──node data/convertMap.js──▶  gentle.js
   ├─ tile layers        → bgtiles, objmap
   ├─ collision layer    → collision          (new, §5)
   ├─ object layer "anchors" → anchors        (new; name + rect + description property)
   └─ animation objects  → animatedsprites
```

No new tool. `convertMap.js` already takes the Tiled JSON and transposes it; it gains two
emitters.

## 5. Collision, resolved

### 5.1 One bitmap, two sources

```
blocked(tile) ⟺ static collision[x][y]
              ∨ ∃ entity e : tile ∈ rect(e.anchor) ∧ e.physics.blocks_movement
              ∨ ∃ player p : distance(p.position, tile) < COLLISION_THRESHOLD
```

The third clause is unchanged (`convex/aiTown/movement.ts:182-186`). The first replaces the
`objectTiles` scan. The second is new and is what makes `05` §6.2 work.

`collision` is a separate export from `objmap`, so "drawn" and "solid" stop being the same
statement. This fixes §2.2's cosmetic problem for free.

**Back-compatibility:** if a `maps` row has no `collision` field, derive it at load with
today's rule — non-empty in any object layer means solid. `data/gentle.js` keeps working
unmigrated, and the stock town remains a valid control (`05` §13, A1).

### 5.2 The loader subtracts mutable rects

A story prop that can open must not be solid in the static layer. Rather than trusting the
map author to remember, **the loader clears the static collision bits under every anchor
occupied by an entity whose `physics` is mutable**, and emits a warning naming the anchor
when it had to. The entity's own `blocks_movement` then becomes the only authority over
those tiles.

This is deliberately a load-time repair rather than a validation error: the map author's
correct instinct is to draw a door as solid, and the failure it would otherwise cause (§2.2)
is invisible at author time and hard to diagnose at run time.

The visual tile stays. Only the collision bit is cleared.

### 5.3 The overlay is an index, not a scan

`blocked()` is called on every A\* expansion and every position update, synchronously, in a
16 ms tick (`05` §1). A linear scan over entities per expansion is the wrong shape even at
small counts.

Maintain a **dynamic collision overlay**: a sparse `tile → count of blocking entities` map,
built when `Game` loads and mutated only when an entity's `physics.blocks_movement` changes.
Lookup stays O(1) and the tick loop's cost is unchanged from today.

The overlay is derived from world-document state, so it is rebuilt on load, never persisted,
and has no replay implications.

## 6. Loading: compile the map, load the entities

**The rule: compile what the engine already models; load what it does not.**

### 6.1 Map → compiler

`init` copies the map module into the `maps` row field for field (`convex/init.ts:70-80`).
There is nothing to interpret. Extend `convertMap.js` to emit `collision` and `anchors`, add
the two fields to `serializedWorldMap` (`convex/aiTown/worldMap.ts:18-31`), and terrain
needs no further engine work in either branch. A runtime loader for tile arrays would be
ceremony around a memcpy.

### 6.2 Entities → loader. Not a compiler targeting `data/characters.ts`

The tempting shortcut is to translate `world.json` down into the existing
`Descriptions` array (`data/characters.ts:10`) and change nothing else. It does not work,
and it fails in a way that gets worse over time.

`Descriptions` is `{ name, character, identity, plan }`. It cannot express a prop, a fixed
actor, an anchor, a physics projection, a state contract, or a god. A compiler targeting it
would have to invent side-channels for every one of those — which is a loader, with an extra
build step and a worse error surface.

Three reasons beyond expressiveness:

1. **Validation needs the map.** `04` §12 rule 7 and `05` §12 rules 3–4 are cross-references
   into the anchor and sprite tables, and §5.2's subtraction needs both files at once. A
   loader checks them against the map row it just wrote.
2. **The input log must be self-contained.** `createAgent` today carries
   `{ descriptionIndex }` (`convex/aiTown/agentInputs.ts:119-124`) — a pointer into a
   compiled TypeScript artifact. Recompile `characters.ts` and every historical input
   silently re-means. `05` §9 and §10 rest on the log being authoritative, so entity
   creation must carry content, or a `blobs` hash (`05` §9.5). That is a `createEntity`
   input emitted by a loader, not a build step.
3. **Provenance.** `world.json` is the artifact to diff, version, and hand to evals.
   Interposing a generated `.ts` means the file under review is not the file that ran.

### 6.3 What does not change

`data/characters.ts:69` — the `characters` array of `{ name, textureUrl, spritesheetData,
speed }` — is already the right thing: a body registry keyed by name. `world.json`'s
`character` and `sprite` fields reference it unchanged. `Player.join` already takes
`(name, character, description)` (`convex/aiTown/player.ts:212-234`), so tier (a) is nearly
a drop-in.

The `Descriptions` array stays too, and the stock boot path stays working. It is the
experimental control.

## 7. Concrete changes

**`data/convertMap.js`**
- Emit `collision` as `boolean[x][y]` from a designated Tiled layer.
- Emit `anchors` from a Tiled object layer, reading `description` from a custom property.

**`convex/aiTown/worldMap.ts`**
- Add `collision: v.array(v.array(v.boolean()))` and `anchors: v.record(...)` to
  `serializedWorldMap` (`:18-31`), both optional for back-compat.
- `WorldMap` derives `collision` from `objectTiles` when absent (§5.1).

**`convex/aiTown/movement.ts`**
- `blockedWithPositions` reads `map.collision` instead of scanning `objectTiles` (`:178-181`).
- Consult the dynamic overlay (§5.3).

**`convex/init.ts`**
- Pass the two new fields into the `maps` insert (`:70-80`).
- Load, validate, and apply `world.json`; clear static collision under mutable anchors
  (§5.2); emit `createEntity` inputs.

**`convex/aiTown/agentInputs.ts`**
- `createEntity` alongside `createAgent`, carrying `{ id, kind, mobile?, name?, character?,
  sprite?, anchor, persona?, description?, state?, memory?, physics }`.

**Client**
- `PixiStaticMap.tsx:47` composites `bgTiles` + `objectTiles` into one static layer, and
  `PixiGame.tsx` renders players. **Nothing renders a prop.** Tier (b) and (c) entities need
  a sprite drawn at their anchor with a click target — this is real work that neither `04`
  nor `05` scoped, and it is a consequence of taking props seriously, not of this split.

## 8. Validation

Replacing `05` §12 rules 3–4, 8 and 10, and `04` §12 rules 7–8. `05` rule 9 —
`initial_memory` requires `initial_state` — survives unchanged.

**Structural**
1. Every referenced `anchor` exists in the loaded map's `anchors`.
2. Every anchor rect lies inside `[0, mapwidth) × [0, mapheight)`.
3. Every referenced `character` and `sprite` exists in its table.

**Occupancy**
4. Two entities with mutable `physics` may not share a tile — **warning**, since stacking is
   coherent but almost always a mistake.
5. A mobile actor's `spawn` anchor must contain at least one tile that is free after §5.2's
   subtraction — otherwise the entity cannot be placed. **Error.**
6. Static collision under a mutable entity's anchor is cleared with a **warning** (§5.2), not
   rejected.

**Tier** (`05` only; `04`'s equivalents are unchanged apart from the loss of tier d)

7. `kind: "prop"` requires `anchor`, and has neither `persona` nor `initial_memory`.
8. Every entity has `initial_state` or `persona`. An entity with neither is decoration and
   belongs in the map — **error**, with a message that says so.

Rule 8 is the split, enforced. It is the one new rule that matters.

## 9. Order of work

1–3 are useful on their own, touch no format decision, and are safe to land before the
branch question (`06` §7) is settled.

1. `convertMap.js` emits `collision` and `anchors`.
2. `serializedWorldMap`, the `maps` row, and `WorldMap` carry both, with the derive-on-absent
   fallback.
3. `blockedWithPositions` reads `collision`; add the dynamic overlay.
4. `createEntity` input; `world.json` loader in `init`; validation §8.
5. Client rendering for fixed actors and props.

`Descriptions` and `data/gentle.js` keep working through all five.

## 10. What this does not solve

**Mobile entities are still one tile.** Anchor rects give footprints to *fixed* things. A
cart that a character pushes needs a multi-tile footprint that moves, which is a pathfinder
change, not a format change. Out of scope; note it before someone authors one.

**Anchors are hand-authored.** A fully generated world — a model that emits terrain *and*
story — would need the map generator to emit the anchor table with descriptions. Nothing
here prevents that; the anchor table is exactly the seam a generator would target. It is not
in scope for either branch's first demo.

**Z-ordering. — Answered in A8.** Entities draw above the flattened map layers and below
players, so a character walking past a door is in front of it. That is the whole rule, and it
holds because an entity is anchored to ground a player can stand on. It would need revisiting for
a tall prop — a wall, a tree — that a player should pass *behind*, which needs a per-entity
draw-order hint the format does not have.

**Anchor granularity is an authoring judgement.** Too few and the writer agent cannot place
anything interesting; too many and the manifest crowds the prompt. Nobody has run this.
Watch it in the same pass as `05` §13 A1.

## 11. Open questions

**B1. Does the anchor manifest fit in a prompt at map scale?**
Every anchor with a prose description enters the writer agent's context. Fifty anchors at
~150 characters is trivial; five hundred is not. If it stops fitting, the manifest needs a
region hierarchy — anchors grouped under named districts, with the agent drilling in — which
is a real design and should be recognised early rather than discovered at generation time.

**B2. Should tier (c) props be allowed to move between anchors?**
`04` has a `move` op (`04` §5, `{ "op": "move", ... }`); a picked-up key is a prop that
changes anchor. This is expressible today — rewrite `anchor` — but it interacts with §5.2's
load-time subtraction, which runs once. Moving a mutable prop needs the overlay updated and
the *old* rect's static bits restored. Decide whether props move before the overlay is
built, not after.

**B3. Does the god need anchor awareness?**
`05` §7 gives the god authority over entity `state` and `physics`. It has no vocabulary for
place. "Move Alice to the north gate" is currently not something it can say. Whether that is
a missing capability or a correct limit is undecided, and it is the same question as B2 one
level up.

**B4. Where does a human player spawn?**
`Player.join` samples the whole map. With anchors, a world file probably wants to declare a
player entry point — but that is a world-level field, not an entity, and neither branch has
a place to put it. Smallest fix: `meta.player_spawn`, an anchor id.
